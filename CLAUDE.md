# concerti-gabri

Concert pages at concerti.gabrifila.me: every user has a public page `/<handle>` ("Sul palco") and `/<handle>/dati` ("I dati"), edited from `/<handle>/modifica` or by AI agents; Gabri's is `/gabrifila`. A logged-in `/` answers 307 to the user's own page, or to `/benvenuto` mid-setup. TanStack Start (SSR) on Vercel, data in Convex (EU), Better Auth on Convex (Google; "Entra con email" only with a real Resend sender or in `VITE_E2E=1` builds); React 19 + TypeScript 7, pnpm only.

- Data lives in Convex and is written only from the owner dashboard (`/<handle>/modifica`), over MCP/API (`/mcp`), by the write-mode Oracolo or by CSV/JSON import, never in code. `shared/seed/gabrifila.ts` (ex `src/data.ts`) is only the seed and the test/parity fixture: `seed:ensure` skips the entries once the profile has any, so editing it changes nothing live. Folders: `shared/` is pure isomorphic code (no React, DOM, secrets or `convex/server`): `model/` types and scales, `lib/` stats, filters and dates, `schema/` the single Zod schema (with `.describe()` texts) from which Convex validators, forms, MCP tools, the Oracolo and the importer all derive, `agent/catalog.ts` the agent operations, `sections.ts`, `theme.ts`, `labels.ts` (first-person labels by grammatical `forma` f/m/n); `src/` is the Start app: `routes/`, `dashboard/` (public page cards), `modifica/` (the owner's management app, below), `server/oracolo/`, `server/mcp/`, `chat/`, `ui/`; `convex/` holds schema and functions (`lib/builders.ts`, `lib/owner.ts`, `lib/km.ts`, `lib/refs.ts`, the local Better Auth component in `betterAuth/`); `e2e/` is Playwright (`fughe/` = leak checks); `scripts/`. `src/routeTree.gen.ts` and `convex/_generated/` are committed generated files: regenerate them (`vite build`, `convex dev --once`), never hand-merge them.
- Concert vs event: an `entries` row (`Entry`, types in `shared/model/concert.ts`) is either a standalone **`Concert`** (the unit — artist + its own ticket/trip inline) or a **`Festival`**, the only kind of event: one ticket/trip bundling ≥2 concerts in `concerts` (its `name` is the event label; a one-concert festival is unrepresentable — the Zod schema and the tuple type forbid it, so `isFestival` discriminates on the `concerts` array). Each festival concert (`FestivalConcert`) carries its own `artist`/`with`/`voto`/`vicinanza`/`canzoniNote` and an optional `date` for multi-day events; ticket (`cost`/`gift`/`giftFrom`/`accredito`), trip (`from`/`km`) and `comments` stay on the festival — a festival concert has no price and no comment of its own. Stats follow the unit: artist/voto/vicinanza/canzoni/compagni counts and the timeline/year chart are per concert (`flatConcerts`/`concertsOf` flatten every row to `FlatConcert`s); money, km and venue visits are per event/ticket (hints say "biglietti"). The archive has two tables: a flat **Concerti** table (every concert a first-class, independently-sortable row; festival concerts show a festival chip and a muted "festival" marker in Costo/Viaggio) and an **Eventi** table below listing just the festivals with their shared ticket/trip. In the DB people, venue, departure and "regalato da" are ids, so renaming breaks nothing; every external input (MCP, import, Oracolo, forms) uses names, resolved server-side in `convex/lib/refs.ts`, and an unknown name is an error that lists the valid ones.
- Ordinal per-concert scales all rise with the *advantage*, so "bigger = better" holds everywhere and no chart axis is ever inverted: `voto` 1–5, `canzoniNote` 1–5 (or `"na"`), and `vicinanza` 1–6 where **6 = Transenna** (closest) down to 1 = Anello alto. `shared/model/scale.ts` is the single source of `VICINANZA_LABELS`, `CANZONI_NOTE_LABELS` (4 = "Molte", never "Quasi tutte") and `VIC_ORDER`; the dashboard, the Zod descriptions, the MCP tools and the Oracolo all read them. The number is the opposite of a reading order, so lists and axes that go best-first walk `VIC_ORDER` (`[6,5,4,3,2,1]`) instead of counting up: the filter chips, the "Quanto sono vicino" card and the scatter's x axis all keep Transenna first/leftmost that way.
- Each KPI card in `sec-kpis` (`src/dashboard/KPIs.tsx`) carries up to two dots bottom-right (`KpiDots`, `src/ui/KpiDots.tsx`): amber if the rows behind the number include past concerts, teal if they include planned ones (so the money cards show both — they count tickets already bought for future dates). They come from the card's `src` rows, so a dot disappears on its own when the active filters leave that side empty. The maintenance alerts (`VicinanzaAlert`, `VotoAlert`, `FromAlert` in `src/dashboard/Alerts.tsx`) are owner-only: in the SSR of the owner's own pages and in the "da completare" box of `#concerti`, never for visitors.
- `/<handle>/modifica` is a management app (`src/modifica/Scheletro.tsx`; DECISIONI «UX di /modifica»): one view per URL hash (`#concerti` default; `vista.ts` params are enum tokens or opaque ids only, never names or addresses), all 9 sections in the SSR HTML, hidden, each mounted on first visit and then kept alive. Forms open in native `<dialog>` drawers (`ui/Pannello.tsx`: non-modal from 1024 px, sheets below) that live in the hash behind one `useBlocker` unsaved-changes guard; other UI opens the concert drawer through the editor bridge `useEditorConcerti().apri()` (`editor.tsx`; `modo: "scheda"` returns the values without writing). Writes go through `useScrittura` (`ui/Toast.tsx`): errors inline, success as a `role=status` toast whose «Annulla» is found client-side by diffing `activity.list` (`annulla.ts`; never for logos, addresses, handle or import). The write-mode Oracolo is one never-unmounted `dialog#oracolo` (`oracolo/Contenitore.tsx`), docked right from 1024 px; its concert card lives in `src/modifica/scheda/` (`bozza.ts` pure, `store.ts` drafts per toolCallId, CSS in `oracolo/chat.css`); a card can't be decided while its «Modulo completo» drawer is open (`moduloAperto`), and leaving `/modifica` with a hand-edited card asks first. CSS is `mf-*` in `sezioni/modifica.css`, colours only from tokens. e2e: switch views with `vaiA()` and open row menus with `menuRiga()` (`e2e/helpers/modifica.ts`; hidden views are invisible to `getByRole`); `e2e/modifica-accessibilita.spec.ts` with `e2e/helpers/accessibilita.ts` checks contrast, focus and 44 px targets; `e2e/screenshot.spec.ts` writes `e2e-shots/ux/`; card specs need `ORACOLO_FAKE=1` (`e2e/oracolo-scheda.spec.ts`).
- `comments` (optional, per event) is the owner's free-text remark on an evening — the only free-text field in the data. It is never printed inline in a table (row heights): the archive's Commenti column holds a button that opens it in `CommentModal` (`src/dashboard/Comments.tsx`), and the "I miei commenti" card (`sec-commenti`) lists the commented events newest-first, 5 at a time. Comments are optional and rare, so the whole card *and* its TOC entry disappear when no event in the active filters has one (the TOC resolves `SECTIONS` against the DOM on open). Page sections live in `SECTIONS` (`shared/sections.ts`, fixed `sec-*` ids): the TOC, the Oracolo's `go_to_section` and the profile layout all derive from it, so add new sections there. The owner's layout can reorder, hide or rename sections; the TOC lists only the visible ones with their custom titles, and a hidden section makes `go_to_section` return `ok:false`.
- Verify with `pnpm build` (`vite build && tsc -b`) and `pnpm vitest run` before every commit; when agents run in parallel use `pnpm build:lock` and `pnpm vitest:lock`. `pnpm e2e` runs Playwright locally against a local Convex backend (takes the e2e lock and waits for 3 GB free; in a worktree via `node scripts/wt.mjs exec -- pnpm e2e`); specs tagged `@sessione` log in with the dev OTP through the API (`e2e/helpers/auth.ts`), `@gemini` ones use the real Gemini key. `PREVIEW_URL=<branch url> pnpm e2e:preview` runs the suite against a Vercel preview. After a build, `node scripts/bundle-guard.mjs` checks the client assets for secret values, server-only env names, `convex/server` and the home coordinates (names only in its output).
- Deploys are git-driven on Vercel: push to `main` → production (the Vercel build runs `convex deploy --cmd 'pnpm build'`, so Convex prod gets schema and functions in the same build); any other pushed branch → a preview at its branch URL with its own Convex deployment `preview/<branch>`, seeded by `--preview-run seed:ensure` when it is created; `fase3/*` and `integrazione` are never built (`git.deploymentEnabled` in `vercel.json`). Never deploy manually, never run `convex deploy` locally (with `CONVEX_DEPLOYMENT` set it targets production) and never run `vercel.json`'s `buildCommand` locally: reproduce a Vercel build with `pnpm build:lock` against a local deployment. Until the switch (`docs/multiutente/SWITCH.md`) production builds are blocked by Vercel's Ignored Build Step and concerti.gabrifila.me is still the old Netlify site from `main`.
- Previews: no PR-and-bot step. A branch's preview is `https://concerti-gabri-git-<branch>-gabrifilas-projects.vercel.app`, protected by Vercel Authentication (bypass with `VERCEL_AUTOMATION_BYPASS_SECRET`, sent only to that origin); read its `ready` state from the Vercel API/CLI (`vercel inspect <url>`) before loading it. Test the map on the branch URL: per-commit URLs are not in the Mapbox token's URL list. Each preview deployment is a separate database: after a Google login there, `gabrifila` must be claimed again (`admin:claimProfile`), also whenever Convex recreates the deployment. After a push, `node scripts/check-setup.mjs --preview` checks that `preview/multiutente` exists, its env names and the seed.
- Reviewing a deploy yourself: `node scripts/preview-shot.mjs <url>` screenshots the full page and reports what loaded (needs `playwright-core` plus the preinstalled Chromium). Chromium loads directly; the Vercel bypass goes only to the project's own deployment origin. The map is really live when `canvas.mapboxgl-canvas` exists, the "Mappa non disponibile" fallback doesn't, and at least one `…vector.pbf` tile answered 200 with none 403: the `pk.` token is restricted by URL on tiles only (styles and fonts answer anyone).
- Poking the Oracolo with curl: `POST /api/chat` takes `{"messages":[{"role":"user","content":"…"}],"forwardedProps":{"handle":"gabrifila"}}` (`threadId` optional, `Origin` only validated when sent) and streams SSE — the `TOOL_CALL_*` events tell you whether `query_concerts` actually ran server-side, so a data question like "quanti concerti ha visto nel 2025?" exercises Gemini and the tool in one call. The model sees only the transcript stored in Convex plus the new question: to continue a thread reuse its `threadId` (and write key); sending a history does nothing. History is per Convex deployment (`chatThreads`, no namespaces): check it with the public `chat.listThreads`/`chat.getThread`.
- Multiutente on t3node: decisions and deviations, env-var map, URLs and deployments are in `docs/multiutente/DECISIONI.md` (dev: the main checkout's production build on port 3150 behind `https://t3node.tail4a8e3b.ts.net:8444`, Convex `agile-leopard-908`; preview `preview/multiutente`; prod `brave-chickadee-534`), the switch checklist in `docs/multiutente/SWITCH.md`, spec and plan in `SPEC.md`/`PIANO.md` (DECISIONI wins over SPEC). `UPSTASH_REDIS_REST_TOKEN_RW` is read-write but only the chat-history migration script may use it, read-only (Gabri's choice), until Upstash is closed.
- Convex for agents and worktrees: every Bash call exports the shared dev deployment (`CONVEX_DEPLOYMENT`, `VITE_CONVEX_*`) and secrets, and the Convex CLI and Vite prefer process env. So in a worktree every convex, vite, vitest and playwright command goes through `node scripts/wt.mjs exec -- <cmd>` (clean env plus `.env.worktree`, a fake CLI token so no cloud deployment is reachable, refuses `deploy`/`--prod`/`--deployment`/prod names), and every Convex CLI call carries `--env-file .env.worktree`. Each worktree has its own anonymous local backend from `scripts/convex-locale.mjs` (`init` once, then `up`/`push`/`seed`/`run`/`down`); don't re-run `init` or `env` on an existing deployment (it regenerates `BETTER_AUTH_SECRET` and breaks JWT signing), and give each worktree its own backend ports (all default to 3210/3211, and `status` only probes the port). Only the orchestrator touches the shared dev `agile-leopard-908`; `preview/<branch>` only with an explicit `--deployment`; never production (`convex deploy`, `--prod`, `brave-chickadee-534`, fnox profile `prod`, Vercel deploy/promote — `.claude/settings.json` denies them, so commit with `git commit -F <file>` when a message names them). Never print env values or `.env*` files, never list process command lines or environments.
- Resources on t3node (4 vCPU, 12 GB): T3 Code puts all agents in one cgroup with MemoryHigh 50% / MemoryMax 75% of RAM (~6/9 GB); on 2026-10-21 seven parallel lanes thrashed the box for hours. Run at most two heavy lanes at a time; heavy commands only under the locks (`pnpm build:lock`; `pnpm vitest:lock`, which shares the build lock; `pnpm e2e`); a memory watchdog may hold the locks while memory is low — wait, don't bypass. Keep local backends and servers down when not in use; port 3100 belongs to worktree e2e runs.
- Departures are private: an address and its coordinates never leave the server. `departureSecrets`, `geocodeDrafts` and `kmPairs` are touched only in `convex/departures.ts` and `convex/lib/km.ts` (`convex/privacy.test.ts` greps it), scheduled jobs get only ids, and the address is set only from the dashboard (`#partenze`, loaded after hydration, never in SSR state). Agents, MCP, the Oracolo and public pages see only the departure name and set/missing; a missing address is an error whose `fix` links `/<handle>/modifica#partenze`. No address or coordinate may reach the bundle, SSR HTML, MCP/API/Oracolo responses, Convex args or errors, logs, Sentry or PostHog (`shared/scrub.ts`, leak specs in `e2e/fughe/`).
- Nickname rule: wherever names are entered (companions, a "regalato da" that is a person, forms, CSV/JSON templates, the agent prompt, MCP tool descriptions, the write-mode Oracolo prompt, the Zod `.describe()` of `with`/`giftFrom`) show "usa soprannomi o diminutivi, non nome e cognome: Marco Rossi → Marco R."; agents shorten full names themselves.
- Every exported Convex function comes from a builder in `convex/lib/builders.ts` (`publicQuery` with explicit `returns`, `ownerQuery`/`ownerMutation`/`ownerAction`, `onboardingMutation`, `internal*`) and labels itself with exactly one of `catalogOp: "<tool>"` (an operation of `shared/agent/catalog.ts`, exposed over MCP and to the write-mode Oracolo), `dashboardOnly: "<reason>"` (addresses, export, account deletion, token management…: agent tokens and `as: "oracolo"` get `solo_dashboard`) or `oracoloOnly: "<reason>"` (only `entries.salvaScheda`, the Oracolo card's save: any caller but `as: "oracolo"` gets `solo_oracolo`; it restricts, it is not a trust boundary); `convex/registry.test.ts` and `convex/isolation.test.ts` enforce it. Owner functions never take a `profileId`, `getOwned` gives the same `not_found` for missing and foreign documents, inputs are validated with Zod inside the handler, errors are `ConvexError {code, messaggio, campo?, fix?}` that never echo values, and secrets are never Convex args. Every write logs to `activity` in the same transaction (author: dashboard, Oracolo, MCP, API key or sistema) and can be undone (`#attivita`, `undo`); deletions and imports above 10 rows need confirmation.
- Venues are a shared Convex catalog (`venues`/`cities`), geocoded server-side with OpenStreetMap Nominatim (not Mapbox, see DECISIONI): nobody types coordinates. Every concert write (MCP `add_concert`/`update_concert`, the Tour manager card, the form, import) takes venue + city by name and trusts the user: a pair not in the catalog is created on save with the typed name (`source: "utente"`, `convex/lib/venueUtente.ts`, logged outside the write's batch since the catalog is never undone), then `geo.posizioneVenue` finds its position from «name, city» (first POI in that city whose name matches, `stessoNome`, else the town centre, never a street or a house); until then its concerts are `kmPending` and it stays off the map, and `venues.impostaPosizione` writes the coordinates once and computes the waiting km (DECISIONI «Venue per nome»). The card shows a non-blocking «Venue nuova» notice; only a missing city, an ambiguous same-name venue or a name that looks like a street address with a house number (`sembraIndirizzoCivico`) blocks, and the server rejects the latter too. Coordinates are immutable once set. `search_venue` → `add_venue {ref}` stays as an optional path, where an OSM place keeps its OSM name.
- Trip distances (`km`) are computed only server-side in Convex (`convex/lib/km.ts`), never in `src/` or `shared/`: `km = round(d · (1.2 + 0.25·e^(−d/20)) · j)` with `d` the great-circle (haversine) distance departure→venue and `j` drawn once, uniformly from [0.95, 1.07], with `crypto.getRandomValues`. The middle factor converts straight-line to realistic route length (urban trips detour more than highway ones); the random `j` is deliberate and must never be skipped or averaged away — it prevents recovering the home point by intersecting distance circles around the public venue coordinates. Each (departure, venue) pair is drawn once and kept forever in the private `kmPairs` table, so delete/re-add and undo/redo give the same km and nobody can accumulate draws; only correcting a departure address redraws (at most once a day). Seeded concerts keep their legacy km. Without an address the concert is `kmPending` ("—" in Viaggio). Agent-token km probes are a known residual risk (DECISIONI).
- `VITE_MAPBOX_TOKEN` (a `pk.` token restricted by URL: Mapbox checks the `Referer`) is in fnox and in Vercel Production + Preview, so pages must never send `Referrer-Policy: no-referrer`/`same-origin` — never commit tokens.
- AI chat ("L'Oracolo" in the UI), one per page: `POST /api/chat` (`src/routes/api/chat/index.ts` → `src/server/oracolo/`, TanStack AI + Gemini) answers only on that page's data (`pages.byHandle`), about the owner in third person with the page's `forma`. `query_concerts`, `report_unsupported_query` and `web_search` run server-side; filters, navigation and `set_visitor_theme` (the visitor's `tema` cookie) are browser tools in `src/chat/tools.ts`. General music questions go through `web_search` — a nested Gemini call with Google Search grounding only (the Gemini API rejects `google_search` mixed with function declarations in one request, so never combine them); the system prompt fences it to music/concert topics, and the owner's data still comes only from `query_concerts`. History is in Convex `chatThreads`: reading is public, continuing requires the thread's write key (stored as SHA-256; the key lives only in the starter browser's localStorage). Write mode is `POST /api/chat/scrittura` (shown as «Tour manager» in the UI; code and data keep `oracolo`), only for the logged-in owner on `/<handle>/modifica` (same-origin `Origin` required): catalog tools with `as: "oracolo"` except `add_concert`/`update_concert` (kept for MCP/API), no `web_search`, approval in chat for deletions, imports, `undo`, `merge_person` and `set_wishlist`, private `visibility: "proprietario"` threads, metadata-only logs. In write mode concerts and festivals are written only through `propose_concert` (`src/server/oracolo/proposta.ts`, not in the catalog): the call pauses the run (`needsApproval`) and the chat shows an editable card; Salva resolves the approval with `{approved: true, editedArgs}` and runs `entries.salvaScheda` (one activity batch with the new people, "regalato da" and name-only departure, km at once, one undo); Scarta, or text typed while a card is open, resolves it with the typed reject `{motivo, nota?, bozza?}`. `propostaConcertoInput` (`shared/schema/proposta.ts`) must stay static: any change, descriptions included, makes cards pending across a deploy stale. Write-route limits (`LIMITI_SCRITTURA`): text 4000, resume 16000, 80 messages, too long = 413 (public chat 1500/2000/40). Rate limits are in `convex/rateLimits.ts` (names are a contract). The Start server and its Convex deployment must share `CHAT_SERVER_SECRET`, otherwise `/api/chat` answers 503.
- TS in the modules split out of the old `App.tsx` (`src/dashboard/`, `src/shell/`, `src/ritratto/`, …) is deliberately loose (converted from untyped JSX): tighten types opportunistically, no blanket refactors.
