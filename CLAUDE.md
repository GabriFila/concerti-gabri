# concerti-gabri

Concert dashboard at concerti.gabrifila.me. Vite 8 + React 19 + TypeScript 7, pnpm only.

- Concert data lives in `src/data.ts` (typed: bad enum values fail the build). App code in `src/App.tsx`, styles in `src/styles.css`.
- Concert vs event: an `ALLDATA` row (`Entry`) is either a standalone **`Concert`** (the unit — artist + its own ticket/trip inline) or a **`Festival`**, the only kind of event: one ticket/trip bundling ≥2 concerts in `concerts` (its `name` is the event label; a one-concert festival is unrepresentable — the tuple type forbids it, so `isFestival` discriminates on the `concerts` array). Each festival concert (`FestivalConcert`) carries its own `artist`/`with`/`voto`/`vicinanza`/`canzoniNote` and an optional `date` for multi-day events; ticket (`cost`/`gift`/`accredito`), trip (`from`/`km`) and `comments` stay on the festival — a festival concert has no price and no comment of its own. Stats follow the unit: artist/voto/vicinanza/canzoni/compagni counts and the timeline/year chart are per concert (`flatConcerts`/`concertsOf` flatten every row to `FlatConcert`s); money, km and venue visits are per event/ticket (hints say "biglietti"). The archive has two tables: a flat **Concerti** table (every concert a first-class, independently-sortable row; festival concerts show a festival chip and a muted "festival" marker in Costo/Viaggio) and an **Eventi** table below listing just the festivals with their shared ticket/trip.
- Ordinal per-concert scales all rise with the *advantage*, so "bigger = better" holds everywhere and no chart axis is ever inverted: `voto` 1–5, `canzoniNote` 1–5, and `vicinanza` 1–6 where **6 = Transenna** (closest) down to 1 = Anello alto (`VICINANZA_LABELS` in `src/data.ts` is the single source of those labels — App.tsx and the chat tools both read it). The number is the opposite of a reading order, so lists and axes that go best-first walk `VIC_ORDER` (`[6,5,4,3,2,1]`) instead of counting up: the filter chips, the "Quanto sono vicino" card and the scatter's x axis all keep Transenna first/leftmost that way.
- Each KPI card in `sec-kpis` carries up to two dots bottom-right (`KpiDots`): amber if the rows behind the number include past concerts, teal if they include planned ones (so the money cards show both — they count tickets already bought for future dates). They come from the card's `src` rows, so a dot disappears on its own when the active filters leave that side empty.
- `comments` (optional, per event) is Gabri's free-text remark on an evening — the only free-text field in the data. It is never printed inline in a table (row heights): the archive's Commenti column holds a button that opens it in `CommentModal`, and the "I miei commenti" card (`sec-commenti`) lists the commented events newest-first, 5 at a time. Comments are optional and rare, so the whole card *and* its TOC entry disappear when no event in the active filters has one (the TOC resolves `SECTIONS` against the DOM on open) — a hidden section makes `go_to_section` return `ok:false`.
- Verify with `pnpm build` (typecheck + build) before every commit.
- Deploys are git-driven: push to `main` → production; PRs → deploy previews. Never deploy manually.
- At the start of a session, open a PR for the working branch, then wait for Netlify's bot to comment on that PR with the deploy preview URL and report that URL back to the user (previews build per PR, so the link is how they see the change live).
- A new venue/city needs coordinates in `VENUE_COORDS`/`CITY_COORDS` (in `src/data.ts`), otherwise the map silently skips it — the types can't catch this.
- Trip distances (`km` per concert in `src/data.ts`) are precomputed offline, never derived in app code: home coordinates and the distance formula must not ship in the public bundle (`src/`). Recipe for a new concert with a `from`: if the same (`from`, venue) pair already has a `km` on another concert, reuse that exact value; otherwise take home `[lng,lat]` — Milano `[9.1694, 45.4600]`, Genova `[8.9487069, 44.4008906]` — and dest `VENUE_COORDS[venue] || CITY_COORDS[city]`, compute great-circle `d` km (haversine), then `km = round(d · (1.2 + 0.25·e^(−d/20)) · j)` with `j` drawn uniformly once from [0.95, 1.07]. The middle factor converts straight-line to realistic route length (urban trips detour more than highway ones); the random `j` is deliberate and must never be skipped or averaged away — it prevents recovering the home point by intersecting distance circles around the public venue coordinates. Consistency with existing values matters less than keeping the jitter.
- `VITE_MAPBOX_TOKEN` (Mapbox pk. token) is set in Netlify env vars — never commit tokens.
- AI chat ("L'Oracolo" in the UI): UI in `src/chat/`, endpoint in `netlify/functions/chat.mts` (TanStack AI + Gemini; server env vars listed in `.env.example`). General music questions are answered via the `web_search` server tool — a nested Gemini call with Google Search grounding only (the Gemini API rejects `google_search` mixed with function declarations in one request, so never combine them); the system prompt fences it to music/concert topics, and Gabri's own data still comes only from the `query_concerts` tool. The Oracolo has a voice (half seer of the archive, half friend who was at the gigs): the `VOICE` block of the system prompt owns it, and it is written in two languages on purpose — the *rules* in English, where instruction-following is strongest and the rest of the prompt already lives, the *examples* in Italian verbatim, because they are samples of the output and no English sentence can specify an Italian rhythm. The two halves are assigned to different parts of the sentence on purpose — the seer to the FACT (compressed, declarative, stated as known rather than looked up), the friend to the REMARK (a judgment in spoken Italian) — because a persona described only as an adjective produces nothing, and the model happily narrates flat prose while obeying every rule about word order. The friend half must never remember or claim to have been there: warmth comes from how the facts are said, never from experience added to them. The voice may only ever change the words: numbers, names and ranking order still come from the tools verbatim (`NUMBERS & NAMES` wins over `VOICE`, and `VOICE` says so itself). `VOICE` is deliberately the LAST block of the prompt: when it sat in the middle, the ten lines of "rules you must never break" that followed it won the tone back and answers went neutral again. Its examples must cover the *awkward* cases too (a caveat about gifts/missing prices, a count that includes an upcoming concert), not just the clean ones — whatever the examples don't cover comes out in the model's default register. The examples carry invented figures, so each one is annotated with the tool fields it came from (`tool: totalCost 487, eventCount 11`) and uses placeholder names: an unannotated constant gets copied into a real answer sooner or later — that is exactly how "tre regali" once reached a year that had two. For the same reason every count the model might want has its own field in the `query_concerts` result (`giftCount`/`accreditoCount`/`unknownCostCount` next to `costKnownCount`): asking it to count `regalo` lines in the concert list is asking it to be wrong. Temperature is 0.55 — colder and the persona collapses back into two or three stock phrasings. Page sections live in `SECTIONS` (`src/chat/tools.ts`) — the TOC and the chat's navigation tool both derive from it, so add new sections there. Conversations are logged to Upstash Redis under `concerti:chat:log:*` (TTL-bounded, keyed by the client thread id) and served back by `chat-history.mts` (`/api/chat/history`): reading is public (deliberate — no accounts), continuing requires the thread's write key, which lives only in the owner browser's localStorage. Non-production deploys (previews/branch deploys/local dev) log to the separate `concerti:chat:log:preview:*` namespace — kept for debugging, never listed in production's public history; each endpoint reads the namespace its own deploy context writes. Shared key layout in `src/chat/chatlog.ts`.
- TS in `App.tsx` is deliberately loose (converted from untyped JSX): tighten types opportunistically, no blanket refactors.
